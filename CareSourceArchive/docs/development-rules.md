# CareSource Archive — Development Rules

Rules that govern how code is written, tested, and tracked during implementation. These override default agent behavior.

---

## 1. Testing

### Tests come from requirements, not code

Write tests by reading `requirements.md` (Section 2) and `features.md` — never by reading the implementation. The test file for a module is the **first file created**, before any implementation code exists.

Workflow per module:
```
Read requirements → Write test file → Run tests (all fail) → Write implementation → Run tests (all pass)
```

If a test needs to change because the requirement was misunderstood, update the test and document why — don't silently adjust tests to match code behavior.

### Test folder structure

```
tests/
├── conftest.py            # Shared fixtures: mock_spark, mock_run_context, mock_audit
├── unit/                  # All modules — pure functions + classes with mocked spark
│   ├── test_utils.py
│   ├── test_config.py
│   ├── test_conditions.py
│   ├── test_exceptions.py
│   ├── test_scanner.py
│   ├── test_archiver.py     # ArchiveEngine with mocked spark
│   ├── test_rehydrator.py   # RehydrationEngine with mocked spark
│   └── test_audit.py        # AuditLogger with mocked spark
├── integration/           # End-to-end through notebooks (requires Spark + cluster)
│   ├── test_archive_flow.py
│   ├── test_rehydrate_flow.py
│   └── test_audit_flow.py
└── interactive/           # Manual testing scripts for ad-hoc validation on Databricks
    ├── try_config_load.py
    ├── try_archive_single_table.py
    ├── try_rehydrate.py
    └── try_scanner.py
```

- **`unit/`** — Runs locally with `uv run pytest`, no cluster needed. Pure functions (config, conditions, exceptions) need no mocks. Classes (archiver, rehydrator, audit) receive a mocked `spark` via constructor — tests verify the class calls the right SQL without executing it.
- **`integration/`** — End-to-end flows through notebooks on a Databricks cluster. Real Spark, real Delta tables, real audit entries. Validates that the SQL generated by classes actually works.
- **`interactive/`** — Throwaway scripts for manually exercising a module against real data. Not part of CI. Useful for quick validation during development.

### Mocking approach

Classes receive `spark` as a constructor parameter. In unit tests, pass a `MagicMock` instead. Notebooks handle `dbutils` — classes never see it.

**Shared fixtures** in `tests/conftest.py`:

```python
@pytest.fixture
def mock_spark():
    return MagicMock(spec=SparkSession)

@pytest.fixture
def mock_run_context():
    return RunContext(
        settings={"audit_catalog": "test", "audit_schema": "audit", ...},
        secrets={"warehouse_id": "test-warehouse"},
        job_context={"workspace_id": "123", "job_id": None, "job_run_id": None, "task_run_id": None},
        archive_run_id="test-run-id-0000",
    )

@pytest.fixture
def mock_audit(mock_run_context, mock_spark):
    return MagicMock(spec=AuditLogger)
```

**Unit test pattern** — verify the class asked Spark to do the right thing:

```python
def test_audit_logs_started_status(mock_spark, mock_run_context):
    audit = AuditLogger(mock_run_context, mock_spark)
    audit.log_archive(table="health.claims.member", year=2020, status="STARTED", count=50000)

    mock_spark.sql.assert_called_once()
    sql = mock_spark.sql.call_args[0][0]
    assert "STARTED" in sql
    assert "health.claims.member" in sql
```

**What mocks verify vs what integration tests verify:**

| Unit tests (mocked spark) | Integration tests (real cluster) |
|---------------------------|----------------------------------|
| Correct SQL generated | SQL executes without errors |
| Right status transitions | Data actually moves to archive storage |
| Error paths raise correct exceptions | Audit rows appear in Delta table |
| Concurrency logic works | External tables resolve to data |

## 2. SDK and API Usage

### Use Databricks SDK and plugins

- Before writing any Databricks API call, use the **Databricks CLI plugin skill** and **Context7 MCP** to look up the correct SDK signatures.
- Prefer the **Databricks Python SDK** (`databricks-sdk`) over raw REST calls or `spark.sql()` for platform operations (jobs, catalogs, warehouses, etc.).
- If no SDK method exists for something, **flag it to the developer** before improvising — don't silently fall back to REST or shell commands.

### Verify before using

Never guess at an SDK method signature. The correct workflow:
```
Need an API → Check Databricks skill/Context7 → Confirm method exists → Use it
```

## 3. Code Quality

### Think before writing

Behave like a senior developer with production experience. Before writing any function:
1. Identify what the function does and what it returns
2. Consider edge cases and failure modes
3. Check if the logic already exists elsewhere in the codebase
4. Critically review your approach before committing to it

### Simple and readable

Write code that a human can read in one pass. Prefer:
- Explicit over clever
- Flat over nested
- Named variables over inline expressions
- Short functions with clear names over long functions with comments

### No comments during development

Code is changing rapidly during implementation. Comments will go stale and create noise. Skip inline comments for now — they will be added in a dedicated pass after testing is complete and the code is stable.

### No code duplication

Do not repeat logic across modules. If you find yourself writing the same pattern twice:
1. Check if a shared utility already exists in `src/utils.py`
2. If not, **ask the developer** before extracting — don't silently create new shared functions that might not belong in utils

### Avoid overusing `collect()`, `show()`, and `display()`

These APIs materialize rows on the driver or render large outputs for interactive viewing. Overuse causes driver OOM, slow jobs, and unnecessary cost on real table sizes.

| API | Role | Guidance |
|-----|------|------------|
| `collect()` | Brings **all** rows to the driver | Use only on DataFrames that are provably tiny (tests, or after `limit()` with a small bound). Never `collect()` a full production partition or table. |
| `show()` | Prints rows to stdout | Acceptable in notebooks while debugging. **Do not** use in `src/` library code or scheduled job paths; prefer logging counts, keys, or error context — not full row dumps. |
| `display()` | Notebook HTML table (Databricks) | **Notebooks only.** Not available or appropriate in packaged modules. Library code under `src/` must not call `display()`. |

**Prefer instead:**

- Keep work distributed: `write`, `saveAsTable`, `insertInto`, joins, `groupBy`, `agg` — let executors do the heavy work.
- When you need a small sample on the driver: `first()`, `head(n)`, or `take(n)` with a fixed small `n` — not unbounded `collect()`.
- For row counts: `count()` or aggregate on the cluster rather than `collect()` + `len()`.
- In tests, build minimal DataFrames so `collect()` is obviously safe.

## 4. Error Handling

### Use the exception hierarchy

All errors must use the custom exceptions defined in `src/exceptions.py`:

- `ArchiveConfigError` — config validation failures. Raised during `generate_parameters` or `load_settings()`. Hard stop — no ForEach tasks launch.
- `ArchiveOperationError` — runtime failures for one table. Raised during archive or rehydration. The failed task is logged to audit as `FAILED`; other ForEach tasks continue.
- `ArchiveVerificationError` — count mismatches or concurrent run detection. The delete step is aborted for that table. Never silenced.

Do not catch generic `Exception` in engine code except to wrap it in one of the above:

```python
except Exception as e:
    raise ArchiveOperationError(f"...context...{e}") from e
```

### Error messages must be actionable

Every exception message must include enough context for a data engineer to diagnose the issue from the audit table or job logs:
- Table identifier (catalog.schema.table)
- Year (if applicable)
- Operation being performed
- Root cause (original exception text)
- For custom_sql failures: the SQL text that failed

## 5. Application Logging

### Use Python `logging`, not print

Every module gets a logger: `logger = logging.getLogger("caresource_archive.{module}")`. No `print()` statements.

### Log levels

| Level | Use for |
|-------|---------|
| `DEBUG` | SQL generation, config merge details, path calculations |
| `INFO` | Table/year being processed, skip reasons, completion counts |
| `WARNING` | Empty custom_sql results, unusual counts |
| `ERROR` | NULL date records found (required value missing), operation failures with exception details |

### Format

Logging is configured once per notebook via `configure_logging()` in utils. Format: `[{timestamp}] [{level}] [{archive_run_id}] [{table}] {message}`.

Do not configure logging inside module code — only in notebooks.

## 6. Modularity and Parallelism

### Independent modules, independent tests

Each `src/*.py` module must be testable on its own. A module's tests should pass without importing other modules (except `utils.py` and `exceptions.py` which are shared dependencies).

This enables:
- Parallel development via subagents — each agent owns one module + its test file
- Incremental validation — as each module completes, its tests confirm it works before dependents start
- Faster debugging — failures are isolated to one module

### Subagent-friendly structure

When spinning up parallel agents, each agent gets:
- One feature (F1, F2, F3, etc.)
- The corresponding test file to write first
- The source file to implement
- Read access to requirements.md and features.md

## 8. Spark Worker Authentication

### Problem

`dbutils` is not available on Spark workers. Any code inside a UDF (`mapInPandas`, `applyInPandas`, `@pandas_udf`, `@udf`) runs on worker nodes, which have no access to `dbutils.secrets.get()`, notebook-scoped credentials, or driver-side context. Attempting default auth on a worker produces:

```
ValueError: default auth: cannot configure default credentials
```

### The Pattern: Resolve on Driver, Pass to Workers

**Driver** (notebook cell or orchestrator function):
```python
creds = get_credentials(scope="my-scope")
# Returns plain strings: (host, client_id, client_secret)
```

**Closure** (pass credentials into the distributed function):
```python
results_df = df.mapInPandas(
    lambda batch_iter: process_batch(batch_iter, credentials=creds),
    schema=output_schema,
)
```

**Worker** (construct SDK clients with explicit credentials):
```python
def process_batch(batch_iter, credentials):
    host, client_id, client_secret = credentials
    ws = WorkspaceClient(
        host=host, client_id=client_id,
        client_secret=client_secret, auth_type="oauth-m2m",
    )
    for batch_df in batch_iter:
        # ... use ws ...
        yield result_df
```

### Common Mistakes

| Mistake | Why it fails |
|---------|-------------|
| Passing `scope` name to workers | Worker can't resolve it — no `dbutils` |
| Using `WorkspaceClient()` with no args in a UDF | No default credentials on workers |
| Constructing SDK clients at module level | Runs at import time on workers — no auth available |
| Passing plain dicts to `serving_endpoints.query()` | Newer SDK (>= 0.100, including Serverless pre-installed) requires `ChatMessage`/`ChatMessageRole` typed objects |

### SDK Typed Message Objects

When calling LLM endpoints from workers (or anywhere), use SDK types — plain dicts break on newer SDK versions:

```python
from databricks.sdk.service.serving import ChatMessage, ChatMessageRole

ws.serving_endpoints.query(
    name="databricks-meta-llama-3-3-70b-instruct",
    messages=[
        ChatMessage(role=ChatMessageRole.SYSTEM, content="..."),
        ChatMessage(role=ChatMessageRole.USER, content=prompt),
    ],
)
```

### Applies To

This pattern is **required** for any distributed Spark function that calls Databricks APIs:
`mapInPandas`, `applyInPandas`, `mapInArrow`, `@pandas_udf`, `@udf`, `spark.sparkContext.parallelize(...).map(...)`.

It does **not** apply to regular notebook cells (driver), Model Serving endpoints (managed identity), or single-node clusters (works by accident — don't rely on it).

## 9. No DDL in Core Code

### Table creation belongs in setup, not in `src/`

All `CREATE TABLE` and `CREATE SCHEMA` DDL statements must live in the setup notebook (`notebooks/setup_config_tables.py`). Core library code under `src/` must never create tables — it should assume the schema already exists and raise `ArchiveConfigError` if a required table is missing.

**Why:**
- DDL is a deployment concern, not a runtime concern. Mixing the two makes it unclear who owns the schema.
- Setup runs once (or on upgrade). Core code runs repeatedly on every job invocation — it should not silently create infrastructure as a side effect.
- Separating DDL into setup makes schema changes auditable, reviewable, and testable in isolation.

**Pattern — core code checks existence via metadata query, never creates:**
```python
def ensure_table_exists(spark, catalog, schema, table):
    fq = f"{catalog}.{schema}.{table}"
    sql = (
        f"SELECT 1 FROM {catalog}.information_schema.tables "
        f"WHERE table_catalog = {sql_quote(catalog)} "
        f"AND table_schema = {sql_quote(schema)} "
        f"AND table_name = {sql_quote(table)} "
        f"LIMIT 1"
    )
    rows = spark.sql(sql).collect()
    if not rows:
        raise ArchiveConfigError(
            msg=f"Table '{fq}' does not exist. "
                "Run the setup_config_tables job first."
        )
```

**Where DDL lives:**

| Layer | DDL allowed? | Example |
|-------|-------------|---------|
| `notebooks/setup_config_tables.py` | Yes | `CREATE TABLE IF NOT EXISTS ...` for all config and audit tables |
| `src/*.py` | No | Query `information_schema` to verify; raise if missing |
| `notebooks/run_*.py` | No | Orchestration only — delegates to `src/` |

## 10. DRY SQL Statements — Use Shared Helpers for DML

### Don't hand-build the same INSERT, UPDATE, or DELETE patterns in multiple places

When multiple modules construct similar SQL statements (INSERT INTO ... VALUES, UPDATE ... SET, DELETE ... WHERE), extract the repeated logic into shared helper functions in `src/utils.py`. Each call site should express *what* it's inserting, not *how* to format SQL.

**Why:**
- Hand-built SQL f-strings are error-prone — a missed comma, wrong quoting, or column/value mismatch is hard to spot in a 30-line string.
- When multiple modules duplicate the same quoting logic under different names, bugs get fixed in one place but not the other.
- Column lists defined as constants catch schema drift at the call site, not deep inside an f-string.

**What to extract:**

1. **Quoting helpers** — one function per SQL type (`sql_quote`, `sql_str_or_null`, `sql_int`, `sql_int_or_null`, `sql_bool`, `sql_expr`). Never duplicate these across modules.
2. **Statement builders** — functions that assemble the SQL string from a table name, column list, and value list. Callers prepare values with quoting helpers, then pass them to the builder.

**Pattern — shared helpers in `src/utils.py`:**
```python
# Quoting — callers use these to prepare values
def sql_quote(s: str) -> str:
    return "'" + str(s).replace("'", "''") + "'"

def sql_str_or_null(val) -> str:
    return "NULL" if val is None else sql_quote(str(val))

# Builder — callers pass already-quoted values
def build_insert_values_sql(table: str, columns: list[str], values: list[str]) -> str:
    if len(columns) != len(values):
        raise ValueError(f"columns ({len(columns)}) and values ({len(values)}) length mismatch")
    return f"INSERT INTO {table} ({', '.join(columns)}) VALUES ({', '.join(values)})"
```

**Pattern — caller becomes declarative:**
```python
AUDIT_COLUMNS = ["audit_id", "table_name", "year", "status", "created_at"]

def log_archive(self, table, year, status):
    values = [
        sql_quote(str(uuid.uuid4())),
        sql_quote(table),
        sql_int(year),
        sql_quote(status),
        sql_expr("current_timestamp()"),
    ]
    sql = build_insert_values_sql(self._archive_table(), AUDIT_COLUMNS, values)
    self._spark.sql(sql)
```

**Anti-pattern — hand-built f-string with inline quoting:**
```python
# BAD: column list and quoting logic duplicated in every method
sql = f"""INSERT INTO {self._archive_table()} (
  audit_id, table_name, year, status, created_at
) VALUES (
  '{uuid.uuid4()}', '{table}', {int(year)}, '{status}', current_timestamp()
)"""
```

**Applies to:**

| Pattern | Extract to |
|---------|-----------|
| Repeated `INSERT INTO ... VALUES (...)` | `build_insert_values_sql` / `build_multi_insert_values_sql` |
| Repeated quoting (`'val'`, NULL checks, int casts) | `sql_quote`, `sql_str_or_null`, `sql_int`, etc. |
| Shared value tails (job context columns used by multiple methods) | Private helper method on the class |

**Does NOT apply to:**
- One-off SQL in setup notebooks (seed data, DDL) — these run once and clarity matters more than DRY.
- Structurally unique statements (MERGE, INSERT-SELECT, CREATE TABLE) — don't force these into a generic builder.

## 11. Guard Destructive SQL Against Empty Input

### Empty staging sets cause bulk damage

A common pattern is: write rows to a staging table, MERGE staging into a final table, then UPDATE the final table to deactivate rows not found in staging. If the staging set is empty (zero templates, zero scan results, or a filter that matches nothing), the UPDATE deactivates *every* row in the final table that was previously managed by the process.

**Rule:** Before running a MERGE + deactivation sequence, check that the input set is non-empty. If there is nothing to merge, return early — do not run the destructive UPDATE.

**Pattern — guard before merge:**
```python
if not configs:
    return {
        "tables_matched": 0,
        # ... all-zero summary ...
        "scan_run_id": scan_run_id,
    }
# Only reach write_staging / merge / deactivate if configs is non-empty
write_staging(spark, configs, staging_table, scan_run_id)
merge_staging_to_final(spark, staging_table, final_table, scan_run_id)
```

**Anti-pattern — unconditional merge with empty staging:**
```python
# BAD: if configs is empty, write_staging is a no-op, but the UPDATE in
# merge_staging_to_final marks ALL scanner-managed rows inactive
write_staging(spark, configs, staging_table, scan_run_id)
merge_staging_to_final(spark, staging_table, final_table, scan_run_id)
```

**Applies to:** Any workflow that combines INSERT-into-staging + MERGE + UPDATE-to-deactivate-missing. The scanner is the primary example today; any future "sync from source" pattern has the same risk.

## 12. Defensive Dict Access for SQL Row Data

### Rows from `collect()` are dynamic — use `.get()` with explicit errors

Rows returned by `spark.sql(...).collect()` and converted via `.asDict()` are plain dicts. Their keys depend on the table schema, which can evolve independently of the code. Raw `d["column"]` indexing raises `KeyError` — which bypasses the custom exception hierarchy and produces unhelpful error messages.

**Rule:** When accessing columns from SQL row dicts, use `.get()` and raise `ArchiveConfigError` with a descriptive message if the key is missing. Never let `KeyError` escape from `src/` code.

**Pattern:**
```python
cat = d.get("source_catalog")
sch = d.get("source_schema")
if cat is None or sch is None:
    raise ArchiveConfigError(
        msg="template row missing source_catalog or source_schema"
    )
```

**Anti-pattern:**
```python
# BAD: KeyError escapes if column is missing or renamed
key = (d["source_catalog"], d["source_schema"])
```

**Exceptions:** In unit tests where you control the mock data, raw indexing is fine — the test will fail with a clear traceback if the mock is wrong. This rule applies to production code paths that process real Spark rows.

## 13. Remove Dead Parameters Immediately

### Dead parameters become silent API breaks

When a function parameter is no longer used inside the function body, remove it immediately. Dead parameters accumulate risk:

1. **Positional shift** — removing a parameter later changes the meaning of positional arguments. If `run_scanner(spark, settings, dbutils=None, force=False)` drops `dbutils`, any caller using `run_scanner(spark, settings, dbutils_obj)` silently binds `dbutils_obj` to `force`.
2. **False documentation** — callers see the parameter and assume the function uses it, leading to incorrect mental models or wasted effort passing values.
3. **Test noise** — tests pass dead values, making it harder to see what actually matters.

**Rule:** When you discover that a parameter is unused (no references in the function body), remove it in the same change. Update all call sites. If the parameter was part of a public API, note the breaking change in the commit message.

**Applies to:** Function signatures in `src/` modules and notebook-level orchestration functions. Does not apply to interface contracts where the parameter is required by a base class or protocol.

## 28. Handle Views in Table-Only SQL Commands

### `DESCRIBE DETAIL`, `OPTIMIZE`, and `VACUUM` reject views

`SHOW TABLES IN catalog.schema` returns both tables and views. Any code that iterates the result and runs table-only commands (`DESCRIBE DETAIL`, `OPTIMIZE`, `VACUUM`) will fail on views with `EXPECT_TABLE_NOT_VIEW`.

**Rule:** Catch `EXPECT_TABLE_NOT_VIEW` and handle gracefully (skip, return `None`, log).

**Pattern:**
```python
try:
    df = spark.sql(f"DESCRIBE DETAIL {fq}")
except Exception as exc:
    if "EXPECT_TABLE_NOT_VIEW" in str(exc):
        return None
    raise
```

**Applies to:** `get_table_size_gb` in `src/scanner.py` and any future code that runs table-only SQL on objects discovered via `SHOW TABLES`.

## 29. MERGE Clause Order: MATCHED Before NOT MATCHED

### Databricks SQL requires `WHEN MATCHED` before `WHEN NOT MATCHED`

Placing `WHEN NOT MATCHED THEN INSERT` before `WHEN MATCHED THEN UPDATE` causes `PARSE_SYNTAX_ERROR` on Databricks (even though standard SQL allows either order).

**Rule:** Always write MERGE with `WHEN MATCHED` clauses first, then `WHEN NOT MATCHED`.

## 30. DDL Nullability Must Match All Code Paths

### Scanner-generated rows may have NULL in columns that manual rows always populate

When a table is created with `NOT NULL` on a column (e.g. `date_column`), every code path that inserts into that table must provide a value. The scanner inserts rows for unmatched/ambiguous tables where `date_column` is legitimately unknown.

**Rule:** Before adding `NOT NULL` to a DDL column, verify that *every* writer — including the scanner, manual inserts, and future MERGE sources — can always provide a non-null value. If any code path produces NULL, make the column nullable and document when NULL is expected.

**Applies to:** `table_configs.date_column` (nullable: NULL means no date column matched). Review all `NOT NULL` constraints in `setup_config_tables.py` against the full set of writers.

## 27. Bundle-Aware sys.path for Notebooks

### DABs notebooks cannot import `src` without help

Databricks Asset Bundles deploy `notebooks/` and `src/` as siblings under the bundle `files/` root. When a notebook task runs, Python's `sys.path` does not include the bundle root, so `from src.config import ...` raises `ModuleNotFoundError`.

**Rule:** Every notebook that imports from `src/` must include a `sys.path` cell as its **first** `# COMMAND ----------` block, before any `from src.xxx import ...` statements.

**Pattern — first cell of every importing notebook:**
```python
# COMMAND ----------
import os, sys
_nb_path = dbutils.notebook.entry_point.getDbutils().notebook().getContext().notebookPath().get()
_bundle_root = os.path.dirname(os.path.dirname(_nb_path))
if not _bundle_root.startswith("/Workspace"):
    _bundle_root = "/Workspace" + _bundle_root
sys.path.insert(0, _bundle_root)
```

Databricks notebooks do not define `__file__`. Instead, use `dbutils.notebook.entry_point` to get the notebook path. `os.path.dirname()` twice navigates from `.../files/notebooks/run_xxx` up to `.../files/` — the bundle root where `src/` lives. The `/Workspace` prefix is added only when the path does not already include it, guarding against environments where `notebookPath()` returns an absolute workspace filesystem path.

**Applies to:** All notebooks that `from src.xxx import ...`:
- `run_scanner.py`, `generate_parameters.py`, `run_archive.py`, `run_rehydrate.py`
- `validate_config.py`, `validate_archives.py`

**Does NOT apply to:** `setup_config_tables.py` and `seed_config.py` — these are self-contained SQL/DDL notebooks with no `src/` imports.

## 31. UC Grants Use Application ID, Not Display Name

### SQL GRANT resolves service principals by Application ID (UUID)

`GRANT ... TO \`caresource-archive-dev\`` fails with `PRINCIPAL_DOES_NOT_EXIST` even when the SP is active in the workspace. UC SQL expects the **Application ID** (UUID), not the display name.

**Correct:**
```sql
GRANT USE CATALOG ON CATALOG dev2_archive TO `ac94d080-96a0-4866-a720-3c60ab629326`;
```

**Wrong:**
```sql
-- PRINCIPAL_DOES_NOT_EXIST
GRANT USE CATALOG ON CATALOG dev2_archive TO `caresource-archive-dev`;
```

Get the Application ID from Account Console (SP detail page) or via CLI: `databricks service-principals list --profile <profile> -o json`.

**Applies to:** All SQL GRANT/REVOKE statements targeting service principals. The CLI `databricks grants update` also uses the Application ID in the `principal` field.

## 32. Unity Catalog Privilege Inheritance

### `USE CATALOG` does not grant `USE SCHEMA`

`USE CATALOG` and `USE SCHEMA` are separate privileges in Unity Catalog. Granting `USE CATALOG` on a catalog does **not** trickle down to schemas — you must grant `USE SCHEMA` explicitly on each schema (or at the catalog level to cover all schemas).

**If the SP effectively owns the catalog** (e.g. a dedicated config catalog like `qa_archive_operations`), simplify with:

```sql
ALTER CATALOG qa_archive_operations OWNER TO `<sp-name>`;
```

Owners implicitly have all privileges on all child objects, eliminating individual grants for that catalog.

**Otherwise, grant both explicitly:**

```sql
GRANT USE CATALOG ON CATALOG qa_archive_operations       TO `<sp-name>`;
```

## 14. Rule Summary

| # | Rule | Enforcement |
|---|------|------------|
| 1 | Tests from requirements, not code | Test file written before implementation file |
| 2 | Three test tiers: unit (mocked spark for classes), integration (end-to-end on cluster), interactive | Folder structure enforced |
| 3 | Use Databricks SDK + Context7 for API calls | Check skill/docs before every SDK call |
| 4 | Prefer Databricks SDK; flag gaps | Ask before falling back to REST/SQL |
| 5 | Think before coding | Review approach critically before writing |
| 6 | Simple, readable code | Explicit over clever |
| 7 | No comments during dev | Comments added after testing is complete |
| 8 | No code duplication | Ask before extracting shared logic |
| 9 | Use custom exception hierarchy | `ArchiveConfigError`, `ArchiveOperationError`, `ArchiveVerificationError` — no generic `Exception` catches |
| 10 | Actionable error messages | Include table, year, operation, root cause in every exception |
| 11 | Use Python `logging`, not print | Logger per module, structured format, configured in notebooks only |
| 12 | Modular and independently testable | Each module testable without siblings |
| 13 | Progress report per file | Update docs/progress-report.md after each file |
| 14 | Live dependency graph | Update docs/code-dependency-graph.md as modules complete |
| 15 | Secrets in scopes, not config files | Warehouse IDs, credentials, and sensitive values go in Databricks secret scopes. Config files hold only non-sensitive settings (catalogs, paths, retention). Access via `dbutils.secrets.get()` through `load_secrets()` |
| 16 | Never log secrets | Secret values must never appear in logs, error messages, or audit records. Use redacted references only |
| 17 | Resolve credentials on driver, pass to workers | UDFs have no `dbutils` — resolve secrets to plain strings on the driver and pass via closure |
| 18 | No default auth in UDFs | Construct `WorkspaceClient` / `VectorSearchClient` with explicit `host`, `client_id`, `client_secret` inside worker functions |
| 19 | Use SDK typed message objects | Use `ChatMessage`/`ChatMessageRole` for `serving_endpoints.query()` — plain dicts fail on newer SDK versions |
| 20 | No unbounded `collect()` | Only `collect()` tiny DataFrames (tests or `limit`+small bound). Prefer distributed writes/aggregates and bounded `take`/`head`/`first` |
| 21 | No `show()` / `display()` in library code | `show()` only in ad-hoc notebook debugging; `display()` notebooks only. Production paths use logging, not row dumps |
| 22 | No DDL in core code | `CREATE TABLE` / `CREATE SCHEMA` lives in `notebooks/setup_config_tables.py` only. `src/` code queries `information_schema` to verify existence and raises `ArchiveConfigError` if missing |
| 23 | DRY SQL statements | Use shared quoting helpers (`sql_quote`, `sql_str_or_null`, etc.) and builder functions (`build_insert_values_sql`) from `src/utils.py`. No hand-built INSERT/UPDATE/DELETE f-strings duplicated across modules |
| 24 | Guard destructive SQL against empty input | Check that staging/input sets are non-empty before running MERGE + deactivation sequences. Empty staging causes bulk deactivation of all managed rows |
| 25 | Defensive dict access for SQL rows | Use `.get()` with explicit `ArchiveConfigError` for columns from `collect()` row dicts. Never let `KeyError` escape from `src/` code |
| 26 | Remove dead parameters immediately | Unused function parameters must be removed in the same change they're discovered. Positional shifts from deferred removal create silent API breaks |
| 27 | Bundle-aware sys.path for notebooks | Every notebook importing from `src/` must have a `sys.path.insert` cell as its first command block. Self-contained SQL notebooks (setup, seed) are exempt |
| 28 | Handle views in table-only SQL commands | Catch `EXPECT_TABLE_NOT_VIEW` when running `DESCRIBE DETAIL` / `OPTIMIZE` / `VACUUM` on objects from `SHOW TABLES` |
| 29 | MERGE clause order: MATCHED before NOT MATCHED | Databricks SQL requires `WHEN MATCHED` clauses before `WHEN NOT MATCHED` |
| 30 | DDL nullability must match all code paths | Verify every writer can provide non-null values before adding `NOT NULL` to a DDL column |
| 31 | UC grants use Application ID, not display name | SQL GRANT resolves SPs by UUID (`application_id`), not display name — display name causes `PRINCIPAL_DOES_NOT_EXIST` |
| 32 | UC privilege inheritance: `USE CATALOG` ≠ `USE SCHEMA` | Grant both explicitly, or make the SP catalog owner for dedicated catalogs |
